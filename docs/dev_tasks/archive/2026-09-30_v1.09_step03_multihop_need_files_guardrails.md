#### 【缺陷根因与修改目标】
```
【根因分析】
根因一：当前 NEED-FILES 多跳逻辑无条件循环开启，每跳重新拼接单条巨型 User 消息，不仅无法复用第 1 跳的前缀缓存，还会反复为模型前轮输出买单；
根因二：在将 NEED-FILES 改为原生多轮（Turn 1 User/Assistant -> Turn 2 User 增量切片）时，若将 Assistant 包含的 reasoning_content（深度推理流）直接回灌进历史，DeepSeek 等大多数支持推理的 upstream 模型会在 HTTP 请求中报 400 Bad Request（拒绝非正文思维链回灌）；
根因三：当前注入预算 max_total_injection_chars: 40000 属于单跳硬限。在多跳累加模式下，如果不引入跨 hop 累积预算池，会导致整体 Token 消耗成倍放大；且在遭遇 400/422 异常时缺少幂等单次单轮降级回退机制；
根因四：若无界读取 live rolling 的 cache_telemetry.jsonl，存在 I/O 阻塞风险；若遇并发轮转可能产生 ENOENT 或半行残缺；且若无单次落盘闩锁（Idempotency Latch），回退重试易引发双倍审计日志落盘；且若闩锁仅为裸闭包布尔量，在异步多线程 offload 下存在 TOCTOU 竞争。

【修改目标】
1. 数据门控开启：引入 MULTI_HOP_DEMAND_THRESHOLD = 0.30 与 MIN_TELEMETRY_SAMPLES = 20 常量，采用有界 tail-read（最多读取最新 50 条）通过 asyncio.to_thread 加锁异步读取 cache_telemetry.jsonl 动态计算多跳需求占比，容忍并发轮转 ENOENT（缺省回退 False）并忽略残缺尾行；采用整数交叉相乘校验 `demand_count * 100 > 30 * sample_count` 杜绝浮点误差；仅当样本数 sample_count >= 20 且 `demand_count * 100 > 30 * sample_count` 时才允许进入多跳，否则短路单跳并记录 multi_hop_skipped_reason；
2. 在构建多轮历史前，实现 strip_reasoning_from_history，纯函数返回新列表（严禁原位修改入参），显式剔除历史 assistant 消息中的 reasoning_content、reasoning 与 thought 属性，仅保留正文 content，彻底杜绝 HTTP 400；
3. 建立 HopBudget 跨跳全局累积字符预算池，单次咨询总切片注入量由运行期解析的 cfg_max_total_chars（默认 consultation.py:126 既有常量 MAX_TOTAL_INJECTION_CHARS）严格受控；明确规定每 hop 必须以【聚合字符数】一次性调用 `budget.consume(total_chars)`，超限返回 False 时严格不扣减计数器（保持原子性），整 hop 整体放弃并置 truncated=True；
4. 明确错误面传播与单次幂等回退契约：在 consultation.py 中捕获 reviewer_engine 上抛的 ReviewerBadRequestError（覆盖 400 与 422），自动剔除增量切片回退为单轮交付；
5. 在调用局部构建线程安全落盘闩锁：采用 `threading.Event` 实例，在任何 `await` 或 offload 之前于当前主事件循环内完成 check-and-set（`if ev.is_set(): return` / `ev.set()`），彻底消除 TOCTOU，同时覆盖 cache_telemetry.jsonl 与 verdicts.jsonl 审计账本，杜绝双倍落盘。
```

#### 【分步改造指引】
1. 在 consultation.py 既有 typing 导入块中追加 `Final`，引入 MULTI_HOP_DEMAND_THRESHOLD 与 MIN_TELEMETRY_SAMPLES 常量，实现经由 `asyncio.to_thread` 有界读取最新 50 条遥测记录的安全门控函数（带 ENOENT 容错与残缺行跳过），门控逻辑采用整数相乘；
2. 实现 strip_reasoning_from_history 辅助函数，纯函数无副作用生成不含 reasoning 相关字段的全新 messages 列表；
3. 实现 HopBudget 类，在 consultation 循环内统一管理跨 hop 累计字符消耗，默认由 cfg_max_total_chars 初始化，每 hop 聚合调用 consume，超限原子失败；
4. 在调用 client.stream_chat 与 acomplete 处增加 `ReviewerBadRequestError` 异常捕获与单次幂等回退降级逻辑，并加入 `threading.Event` 构造的调用局部落盘闩锁（在 await 之前同步 check-and-set，同时受控 telemetry 与 verdicts 两大 sink）；

#### 【防御与边缘校验】
- 预算耗尽时不得进行部分切片注入致使语义撕裂与缓存指纹污染：每 hop 聚合判定，整 hop 整体放弃并置 truncated=True
- reasoning 剥离仅严格作用于历史 assistant 消息，严禁触碰或误删首轮 system 静态前缀与 user 提问文本，且绝不改动入参引用
- 400/422 回退重试最多发生一次，禁止死循环；回退前对 messages 进行深拷贝快照以保证重试幂等性
- 无 telemetry 历史统计文件或样本数不足 MIN_TELEMETRY_SAMPLES (sample_count < 20) 时，保守默认短路关闭多跳，安全退避为单轮交付
- 落盘闩锁独立驻留在调用执行栈内，采用 threading.Event 在 await 前完成原子 check-and-set，严禁入侵 ConsultResult 冻结契约破坏 MCP schema，且必须同时保护 telemetry 与 verdicts 账本
- 遥测记录读取必须在工作线程池执行（asyncio.to_thread），并安全处理并发轮转引发的暂态 ENOENT，严禁在主协程内发生阻塞 I/O
- MULTI_HOP_DEMAND_THRESHOLD 浮点常量主要用于文档与契约声明，运行期判定与单测断言严格以 MULTI_HOP_DEMAND_PERCENT 为唯一 SSOT，遵循整数交叉相乘逻辑 `demand_count * 100 > MULTI_HOP_DEMAND_PERCENT * sample_count`，彻底杜绝浮点精度漂移
- 回退降级分支由单次落盘闩锁保护，严禁重复向 telemetry.jsonl 或 verdicts.jsonl 重复落盘双倍记录
