#### 【缺陷根因与修改目标】
- **根因 1（清单损坏 Fail-Open 致命漏洞，P0-1）**：`manifest.py::load_manifest` 在捕获异常时静默吞下并返回空 `Manifest(records={})`。若清单发生损坏或并发截断，探针将误判为 `NO_LEASE`，回收器误报假性成功，`generation` 计数器归零，导致锁防线彻底击穿。必须改造为 Fail-Closed 并抛出 `ManifestIntegrityError`。
- **根因 2（心跳源缺失）**：`TaskRecord.last_heartbeat_*` 仅在单次状态流转时写入；长任务执行期间无周期性刷新通路，"心跳静默"判据对长任务恒为真，导致误判僵尸。
- **根因 3（跨进程时钟失真）**：`last_heartbeat_monotonic_ns` 跨进程不可比；`last_heartbeat_wall_utc` 受 NTP 回拨影响可能产生负时长。
- **修改目标**：在 `manifest.py` 引入 `ManifestIntegrityError` 与 `touch_heartbeat`（代际/token 双校验原子更新）；在 `server.py` 注册 FastMCP 原生工具 `dev_tasks_heartbeat`（支持 `session_id` 与跨会话防歧义鉴权）。

#### 【缺陷根因与修改目标】
- **根因 1（AB-BA 死锁与跨域非原子崩解，P0-2）**：任务回收涉及任务单 Markdown 文件锁与清单 `manifest.json` 文件锁。若锁序不一，极易与 `dev_tasks_checkout`（先 Markdown 后 Manifest）产生 AB-BA 死锁；且若中途崩溃会发生“清单已释放但任务单仍为执行中”的不一致。必须强制全局锁序：**先获取任务单 Markdown 锁，再获取 Manifest 锁**。
- **根因 2（状态机绕行后门，P0-3）**：`state_machine.VALID_TRANSITIONS` 中已存在 `In Progress -> Confirmed`。若不加约束，外部可通过 `dev_tasks_confirm` 直接将执行中任务重置，绕开回收代际递增。必须在 `server.py::dev_tasks_confirm` 显式阻断此流转，将其严格限定于 Reaper 回收通道。
- **根因 3（回收竞态与 TOCTOU）**：若在探针检查与执行回收之间目标任务恢复并完成，盲目强制回收将破坏正常交付产物。
- **修改目标**：在 `reaper.py` 实现 `reclaim_stale_task`（基于全局一致锁序与双属性 CAS 判定与回收）；在 `state_machine.py` 与 `server.py` 闭环权限门禁；注册 `dev_tasks_reclaim` MCP 工具，要求携带代际与 token 证据或强制确认，CAS 成功后递增 generation 彻底作废旧持有者令牌。

#### 【分步改造指引】
1. **全局锁序控制**：`reclaim_stale_task` 必须遵循 **先 Markdown 锁、后 Manifest 锁** 的全局严格拓扑顺序，杜绝与检出/提交流程的锁竞争死锁。
2. **`reaper.py::reclaim_stale_task`**：双锁保护下：(a) 校验租约存在性，若无则返回 `(False, "no_such_lease")`；(b) 校验 CAS 前置条件（代际与 token），不符则返回幂等成功；(c) 锁内执行探针复核（非 force 下 HEALTHY 拒绝回收）；(d) 更新 `manifest.json` 调用 `release_lease` 递增 generation；(e) 原子重写任务单 Markdown 将状态置为 `⬜ 待确认`。

4. **单测覆盖**：在 `test_reclaim_cas.py` 中测试正常回收、健康任务被拒回收、陈旧代际幂等返回、无租约记录处理、锁序一致性与并发争抢回收。

- **锁序拓扑绝对一致**：全仓所有涉及 Markdown 与 Manifest 的复合操作必须遵循“先 Markdown 锁后 Manifest 锁”，违者直接断言失败。

- **锁内重探防 TOCTOU**：`reclaim_stale_task` 必须在临界区内重新执行健康探针判定，拒绝信任外部传入的历史陈旧证据。
