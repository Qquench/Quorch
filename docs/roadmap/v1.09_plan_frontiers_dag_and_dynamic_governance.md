## 0. 架构裁决与代差对比 (Executive Audit & Gap Matrix)

通过与各大主流 IDE / 前沿 Agent 体系的 Plan 模式横向剖析，Quench 在**微观确定性防御**上构建了独特的工程壁垒，但在**任务依赖拓扑、人机协同粒度、原子回滚机制、上下文精准计量**等宏观架构上存在显著的代差短板。

### 0.1 Quench 的核心护城河 (Defend & Keep)
1. **异构第二模型独立审查门禁 (Heterogeneous Second-Model Review Gate)**:
   - 业界主流（Cursor Plan、Windsurf Cascade、Claude Code）本质均为“同一模型自拟计划、自审自查”，不可避免地受到**自我确认偏差（Confirmation Bias）**的局限；
   - Quench 强制确立 Agile Runner（执行模型）与 Strategic Reviewer（审查模型）的异构物理分离，禁止就地角色扮演，实现了真正意义上的第二视角红队挑刺与质量审计。
2. **物理级确定性拦截 (Physical Deterministic Enforcement)**:
   - 主流编辑器的治理规则多依托 System Prompt 与 Markdown 指引，属于**建议性软约定（Advisory Soft Rules）**；
   - Quench 实现了 PreToolUse 运行时白名单动态拦截、Git Pre-commit 守卫物理阻断、DoD 命令行强制验证与草案物理可行性 Lint 门禁，具备确定性执行力。

### Phase 1: Tokenizer-Aware 上下文预算与截断显式遥测 (Critical)

#### 1.1 问题剖析与根因
- 现有 `quench_stack.yaml` 配置 `reviewer_engine.max_total_injection_chars: 40000` 与 `max_lines_per_slice: 600`。
- 字符与 Token 的兑换比受语言特性严重制约：
  - 英文标准代码：约 $0.25 \sim 0.35\ \text{tok/char}$；
  - 中文技术文档与注释：因 UTF-8 编码与分词粒度，常达 $0.6 \sim 2.0\ \text{tok/char}$。
- 当任务单包含大量中文根因剖析与长代码切片时，40k 字符极易膨胀至 50k~60k Tokens。叠加系统提示、MCP 工具 Schema（15+ 个工具）与历史交互后，**直接突破大模型上下文窗口上限**。
- **致命后果**：底层 HTTP Client 或模型端发生**静默尾部截断**。Reviewer 只能读到半截函数或残缺类型声明，却仍能输出符合六大字段语法的“假裁决”，写入 `verdicts.jsonl` 误导后续执行。

#### 1.2 改造规范与类型契约
1. **废弃字符预算**：在 `.agents/quench_stack.yaml` 中新增 `max_total_tokens`、`reserve_tokens` 与 `max_tokens_per_slice`，保留旧配置但标记弃用告警。
2. **接入本地 Tokenizer 引擎**：
   - 优先通过配置动态载入模型对齐的轻量分词器（如基于 `tiktoken`、`transformers` 或 `deepseek-chat` 对齐算法）；
   - 若环境缺失分词库，必须基于 UTF-8 字节密度使用**严格保守估算**，并打印降级标记。
3. **强制截断遥测 (Truncation Telemetry)**：
   - 装配上下文切片时，若超出预算，禁止悄悄切断；必须返回明确的元数据结构，记录被丢弃的切片来源。

```python
# plugins/quench-dev-tasks/server/reviewer/context_budget.py
from dataclasses import dataclass
from typing import Callable, Sequence

@dataclass(frozen=True)
class InjectionBudget:
    max_total_tokens: int          # 总 Token 预算 (取代 max_total_injection_chars)
    reserve_tokens: int            # 为 System Prompt 与 MCP Tools 预留空间 (默认 8192)
    max_tokens_per_slice: int      # 单切片 Token 上限

@dataclass(frozen=True)
class BudgetResult:
    text: str                      # 装配完成的文本内容
    estimated_tokens: int          # 实际计算出的 Token 总量
    truncated: bool                # 是否触发了主动截断 (绝不允许静默截断)
    dropped_slices: tuple[str, ...] # 被降级/移除的切片路径或标识列表

def enforce_budget(
    slices: Sequence[tuple[str, str, int]],  # (slice_id, content, priority)
    budget: InjectionBudget,
    counter: Callable[[str], int],
) -> BudgetResult:
    """按优先级装配切片。优先保障缺陷根因与目标契约，超限时裁撤低优先级切片并显式置位 truncated。"""
```

### Phase 2: 租约单调 Fencing Token (Epoch) 与原子回滚原语 (Critical)

#### 2.1 会话假死与双写竞态 (Kleppmann Fencing Problem)
- 当前 `governance.lease_ttl_seconds: 300`（5分钟）。中大型重构任务执行常耗时 10~20 分钟以上。
- **竞态场景**：
  1. 会话 A 检出任务 X，开始修改代码；随后因本地垃圾回收、网络阻塞或复杂推理，会话 A 挂起超过 300 秒，心跳中断；
  2. 开发者或自动化脚本在会话 B 中执行 `dev_tasks_checkout(X)`，系统判定租约超时并授予会话 B 锁所有权；
  3. 会话 A 突然恢复，向白名单文件发送写入指令；
  4. 现有的 PreToolUse 钩子仅检查“该文件是否在活动任务的白名单中”，由于任务 X 确实在进行中，**两个会话的写入均被放行**；
  5. 导致文件内容交错覆盖、Git 提交历史混乱，破坏单核串行保证。

#### 2.2 解决方案：单调 Epoch 序列与原子回滚
1. **Fencing Token 注入**：
   - 每次成功检出任务时，全局 CAS 锁递增生成单调递增的 `epoch` 编号（如 101, 102...）；
   - 租约记录保存 `(session_id, epoch, expires_at)`；
   - 写入拦截（PreToolUse）与 Git 守卫必须在上下文校验 `(session_id, epoch)` 是否完全与权威租约一致，**过期 epoch 的写入一律幂等拒绝**。
2. **显式回滚原语 (`dev_tasks_revert`)**：
   - 现有的 `[Rework]` 仅改变了任务单 Markdown 中的 Emoji 状态，已修改到磁盘的代码依然残留；
   - 引入 `dev_tasks_revert(task_id)` 工具：借助 Git 暂存区或临时分支，原子还原工作区至检出前镜像，防止脏代码污染下一轮开发。

### Phase 3: 任务依赖拓扑 DAG 与接口冻结窗口 (High)

#### 3.1 消除“逻辑陈旧”与破坏性变更
- 目前仅凭 `[In Progress]` 单核串行锁，虽然防止了物理并发写冲突，但**无法防止逻辑依赖断裂**：
  - 例如：Task 1 重构了 `AuthService.login()` 签名；Task 2 依赖该服务，但已经提前被标记为 `[Confirmed]`；
  - Task 1 完成后，Task 2 检出执行，若其白名单恰好包含测试文件但未更新断言，测试可能依然因旧逻辑通过，而真实依赖已毁坏。
- **架构升级**：
  1. **元数据声明依赖边**：
     ```markdown
     <!-- quench-task-meta: {"id": "task_2", "depends_on": ["task_1"], "interface_freeze": ["AuthService.login"]} -->
     ```
  2. **检出门禁 (`checkout_allowed`)**：
     - 在调用 `dev_tasks_checkout` 时，遍历 `depends_on` 拓扑列表；若任意依赖任务未处于 `[Completed]` 或 `[Archived]`，拒绝检出并提示阻塞原因。
  3. **接口冻结窗口 (Interface Freeze Window)**：
     - 若某一底层改动被多个下游依赖，必须在【目标签名与类型契约】中声明接口过渡期（保证新旧兼容直至所有依赖方迁移闭环），DoD 必须附带新旧签名共存测试。

### Phase 4: 细粒度人机协同反馈信道 (High)

#### 4.1 改变“整单推翻”的粗暴重做
- 目前任务确认只有 `confirm`（完全接受）或整单回退 `rework`。
- 若分步指引包含 8 个步骤，仅第 5 步存在正则边界歧义，将整单打回重新推演将造成巨大的 Token 浪费，且 Reviewer 在重新生成时极易“按下葫芦浮起瓢”，丢弃前 4 步的高质量推导。
- **改进方案**：
  - `dev_tasks_confirm` 增强入参：
    ```python
    dev_tasks_confirm(
        task_id="task_07",
        action="rework",
        rejected_steps=[5],
        rejection_rationale="第 5 步的正则忽略了 Windows 风格路径的反斜杠转义"
    )
    ```
  - 系统生成局部修正上下文，Reviewer 咨询时仅针对第 5 步实施精准修补（Delta Patching），保留其他已通过步骤。

### Phase 5: 符号级关联注入 (Repo-Map) 与 IDE 原生能力绑定 (Medium)

#### 5.1 符号级关联代替纯行号盲切
- 借鉴 Aider 的 Repo-Map 机制，在分析大型工程时，利用 Tree-sitter 提取项目中所有相关符号的定义与引用关系，通过图排序算法挑选最具关联性的声明注入切片，替代机械的 `1-600` 行切片。

#### 5.2 规则条件动态激活与子代理隔离
- **Globs 条件规则**：借鉴 Cursor `.mdc` 前置元数据，将 `rules/` 中的专有规则（如 Python 编码规范、FastMCP 协议规范）绑定至匹配的文件类型，避免每一次通用交互都注入全量规范导致上下文稀释。
- **Reviewer 子代理沙箱化 (`stream_in_subagent`)**：长达数十轮的架构推演日志与切片应完全约束在独立的 Reviewer 子代理会话内，主会话仅沉淀最终的标准化审查卡（Verdict Card），根治长效会话 Token 膨胀。

## 2. 演进演练与反向破局案例 (Real-World Scenarios)

### 案例 A：中英混排长任务静默截断导致假裁决 (C-1 破局)
- **破局前**：40,000 字符的包含详尽中文缺陷分析与大量类型定义的复杂任务单，实际展开为 54,000 Tokens。外部模型静默丢弃了尾部的防御校验与 DoD 命令。Reviewer 对残缺内容表示“结构完整、准予批准”，导致重大边界漏洞漏网。
- **破局后**：`enforce_budget` 发现实际计算量为 54,000 Tokens，超过 `max_total_tokens: 32000` 上限。系统拒绝静默放行，按照优先级保留根因与契约，主动裁剪辅助切片，并在元数据中回传 `truncated=True, dropped_slices=['auxiliary_context.py']`，Reviewer 显式发出警告并要求缩减范围。

### 案例 B：网络卡顿 300s 租约失效后双会话并发覆写 (C-2 破局)
- **破局前**：会话 A 在编辑过程中因网络闪断卡顿 6 分钟。会话 B 检出同一任务并开始编辑。会话 A 随后恢复重发写工具调用，PreToolUse 放行，两会话交错修改文件，代码严重冲突。
- **破局后**：会话 B 检出时，CAS 将全局任务锁递增为 `epoch: 104`。会话 A 恢复后携带旧有的 `epoch: 103` 试图调用 `write_to_file`。PreToolUse 拦截器对比发现当前权威 epoch 已变更为 104，**立即抛出 `StaleLeaseEpochError` 物理阻断写入**，并提示会话 A 刷新状态。
