# v1.24 全盘架构评审：MCP 原生 Progress 通道 + 长轮询 + Poll 瘦身（方案 A）

## 0. 结论摘要（Verdict）

**方案 A 技术上可行且方向正确，但当前提案存在 4 个必须收敛的红线风险，其中 1 个可能导致 CI 物理门禁全线冻结。**

| 判定 | 内容 |
|---|---|
| ✅ 采纳 | MCP `notifications/progress` 承载运行期心跳；`wait_max_s` 长轮询降压；非终态快照剥离嵌套 `progress` |
| ⚠️ 修正 | ① **不得**把非终态快照砍到 3 字段——必须保留 `log_ref`（见 §2 矩阵，这是无 `progressToken` 宿主的唯一 liveness 信道）；② `dev_reviewer_poll` 的循环逻辑必须下沉 T4，T2 只保留 ctx 桥接；③ 判定 `elapsed_s` 单标量替代嵌套 `progress` 对象；④ 长轮询**必须零锁跨 await**、**零字节写盘** |
| 🚨 高危 | **`ctx: Context` 注入是否改变 `ide_tool_schemas.json` 是本次改造的单点致命依赖**。`git_pre_commit_guard.py` 监控 `SCHEMA_TRIGGER_PATHS`（含 `server.py`）且 fail-closed，任何 schema 字节漂移会阻断全部提交。必须先行 spike 证明零漂移（任务 24.1） |

**诚实收益边界（拒绝过度承诺）**："零主对话流污染" 在物理上不成立。真实收益为：

- 卡片频次：~1 次 / 2s → ~1 次 / 25s（**约 12×** 削减）
- 非终态卡片体积：≈ 380 B → ≈ 160 B（**约 58%** 压缩）
- 支持 progress 的宿主：卡片 Header 原地自刷新，**期间新增 0 张卡**
- 不支持 progress 的宿主（Theia / 部分 Agent Host）：**无 Header 动画，但仍是 1 次 / 25s**

## 1. A/B/C 方案权衡矩阵

| 维度 | **A：MCP Progress + 长轮询 + 瘦身** | B：仅调小轮询间隔（客户端退避） | C：带外哨兵文件（客户端 tail `latest-<sid>.log`） |
|---|---|---|---|
| 开发成本 | 中（~6 任务，跨 T2/T4/文档） | 极低 | 中（需宿主侧文件监听能力） |
| 工具面不变量 | ✅ 16 工具不变（仅加 `ctx` 参数） | ✅ 不变 | ✅ 不变 |
| INV-1~9 合规 | ✅ 全合规（progress 走 FastMCP session，非 `print`） | ✅ | ⚠️ 需宿主具备 FS watch，跨 IDE 不可移植 |
| 宿主覆盖 | ✅ 广（MCP 标准字段） | ✅ 全覆盖 | ❌ 仅桌面 IDE |
| 失败爆炸半径 | 低（进度失败 → fail-open 静默） | 无 | 高（客户端读逻辑各自实现） |
| 短任务延迟 | ✅ 50–250 ms 短路 | ✅ | ✅ |
| 长任务调用频次 | ✅ 1 / 25s | ❌ 无改善（受 `retry_after` 下限 2s 限制） | ✅ 1 / ∞ |
| Token 收益 | ✅ 结构性（频次 × 体积双降） | ❌ 仅频次微降 | ✅ 但引入非 MCP 旁路 |

**裁决：A 为主航道，C 作为隐式兜底保留**。这正是**不可剥离 `log_ref` 的算法级理由**——无 `progressToken` 时，人类/Agent 唯一可观测信道就是 `log_ref` 指向的日志文件。剥离它等于让 Theia 系宿主"眼盲 25 秒"。

## 2. 架构总览与技术原理

```
[Agent Host] ── tools/call dev_reviewer_poll(_meta.progressToken="tok-7")
      │
      ▼
┌──────────────────────────────────────────────────────────────┐
│ T2  server.py :: dev_reviewer_poll                            │
│   ├─ _poll_impl(job_id, wait_max_s, bridge)    ← 可无 FastMCP 直测 │
│   ├─ ProgressBridge.from_context(ctx)          ← token 嗅探        │
│   └─ async for snap in supervisor.watch(...):                     │
│         bridge.emit(snap)  (合流/单调/fail-open)                  │
└───────────────────────┬──────────────────────────────────────┘
                        │ 异步生成器（T2 不持锁、不写盘）
┌───────────────────────▼──────────────────────────────────────┐
│ T4  reviewer_jobs.py :: ReviewerJobSupervisor.watch()          │
│   ├─ 自适应退避 50→100→250→500→1000 ms                          │
│   ├─ anyio.to_thread.run_sync(_read_snapshot_sync)  ← 锁仅在 worker 线程内 │
│   ├─ generation 漂移自愈（reclaim / CANCELLED_PENDING_REAP）      │
│   └─ liveness 探针节流 2.0 s（probe_lease_health 昂贵）           │
└──────────────────────────────────────────────────────────────┘
                        │
      ◀── notifications/progress {token, progress:n, message:"…"}（≤120 B, 1 次/s）
      ◀── tools/call result（终态全量 / 非终态 6 字段 ~160 B）
```

### 2.1 `progressToken` 嗅探与 fail-open 阶梯

```
bridge = ProgressBridge.from_context(ctx)
  ① ctx 为 None                    → bridge=None（单元测试/CLI 直调路径，零开销）
  ② ctx.request_context.meta 缺失  → bridge=None
  ③ meta["progressToken"] 为 None/空 → bridge=None（严格遵循 MCP 规范：未提供则 MUST NOT 发送）
  ④ ctx.report_progress 不存在     → bridge=None（旧版 FastMCP）
  ⑤ 首次 emit 抛任意 Exception     → bridge._disabled = True（一次性熔断，本请求后续零开销）
```

**关键防御（红队发现）**：`Context.report_progress` 的签名在 FastMCP 各版本间不一致——早期版本**无 `message` 关键字**。必须用 `inspect.signature` 探测，无 `message` 时降级为 `report_progress(progress)`。否则在旧宿主上每次 poll 都会抛 `TypeError` 并被熔断，等于功能静默消失且不可诊断。

### 2.2 单调递增保证

`progressToken` 是**按请求**的，因此计数器必须**按请求局部**（`self._counter` 从 1 开始），不可用全局计数器——否则并发 poll 会交叉污染同 token 序列。

- `progress = counter`（整数，严格递增）
- `total = None` → 客户端渲染**不确定进度条**（indeterminate spinner）
- **不传 `total`** 的理由：任务总时长不可知，传 `total = wait_max_s*1000` 会让进度条在 25s 内跑满后假性结束，反直觉

## 3. `dev_reviewer_poll` 长轮询循环重构契约

### 3.1 分层权责（强制）

| 层 | 职责 | 禁止 |
|---|---|---|
| **T2 `server.py`** | `ctx` 桥接、参数钳制、终态/非终态分派 | 禁止持有 `FileLock`；禁止直接读 JobRecord 文件；禁止 `print`（INV-4） |
| **T4 `reviewer_jobs.py`** | `watch()` 异步生成器、退避、代际自愈、探针节流 | 禁止导入 `fastmcp`；禁止 `ctx.report_progress` |

**理由**：`reviewer_jobs.py` 已 `import anyio`，可纯 `anyio` 单测（`pytest.mark.anyio`），无需拉起 FastMCP 运行时；`server.py` 已过大，把 25s 循环塞进去会让 P1~P5 与 schema 导出链路同时承压。

### 3.2 `watch()` 语义契约

```python
async def watch(
    self,
    job_id: str,
    *,
    deadline_monotonic: float,
    min_interval_s: float = 0.05,
    max_interval_s: float = 1.0,
    liveness_probe_interval_s: float = 2.0,
) -> AsyncIterator[PollSnapshot]:
```

| # | 不变量 |
|---|---|
| W1 | 首次 yield 在 **t=0**（≤10 ms），保证短任务 50–250 ms 短路 |
| W2 | 间隔单调升：50→100→250→500→1000 ms 封顶 |
| W3 | 任意 state/phase 变化 → 间隔**重置**为 `min_interval_s` |
| W4 | `time.monotonic() >= deadline_monotonic` 终局 |
| W5 | 终态（`POLL_TERMINAL_STATES`）立即终局 |
| W6 | **锁仅在 `anyio.to_thread.run_sync` 的 worker 线程内获取**，绝不跨 `await` |
| W7 | generation 漂移 → yield 最新快照，**不抛异常**（跨轮自愈） |
| W8 | `anyio` 取消异常**必须透传**，绝不 `except Exception` 吞掉 |
| W9 | `probe_lease_health` 节流 ≤ 1 次 / 2 s（防 25s 内 500 次探针风暴） |
| W10 | 全程零写盘（不写 JobRecord、不写 log、不触发 GC/配额） |

### 3.3 长轮询主循环

```python
async def _poll_impl(job_id: str, wait_max_s: float, bridge: ProgressBridge | None) -> dict:
    jid = validate_job_id(job_id)
    w = _clamp_wait(wait_max_s)              # NaN/inf/<0 → 0.0；bool → TypeError；上限 25.0
    supervisor = _get_supervisor()

    if w <= 0.0:                              # 快路径：单次同步读，~1 ms
        return _snapshot_to_dict(supervisor.read_snapshot(jid))

    last = None
    deadline = time.monotonic() + w
    async for snap in supervisor.watch(jid, deadline_monotonic=deadline):
        last = snap
        if snap.state in POLL_TERMINAL_STATES:
            return _snapshot_to_dict(snap)    # 终态不 emit，客户端随即拆 UI
        if bridge is not None:
            await bridge.emit(snap)           # 内部 fail-open，绝不抛出
    return _snapshot_to_dict(last)
```

## 4. 非终态/终态返回契约瘦身规范

### 4.1 字段演进

| 版本 | `POLL_NONTERMINAL_FIELDS` |
|---|---|
| v1.23 | `{job_id, session_id, state, retry_after_seconds, log_ref, progress}` ← `progress` 是 5 键嵌套对象 |
| **v1.24** | `{job_id, session_id, state, retry_after_seconds, log_ref, elapsed_s}` ← `progress` → 单整数 |

**终态 `POLL_TERMINAL_FIELDS` 严格不变**（回归红线）。

### 4.2 为什么保留 `session_id` 与 `log_ref`

- `log_ref`：无 `progressToken` 宿主的唯一 liveness 信道（§1 裁决依据）
- `session_id`：并发多会话下与 `latest-<sid>.log` 的人工关联；键长 ≤ 128 B 但通常 36 B UUID
- `elapsed_s`：单标量，代价 ~14 B，为 fail-open 宿主保留"任务仍在动"的最低证明

体积估算（最坏情形：64 字符 `job_id` + 40 字符 `log_ref`）：**≈ 210 B**，远低于 `MAX_NONTERMINAL_SNAPSHOT_BYTES = 1024`。

### 4.3 运行时契约守卫（新增）

```python
_NONTERMINAL_ABS_PATH_RE = re.compile(r"^(?:[A-Za-z]:[\\/]|/|\\\\)")

def _assert_nonterminal_contract(d: Mapping[str, Any]) -> None:
    if not set(d) <= POLL_NONTERMINAL_FIELDS:
        raise SnapshotContractViolation(...)          # 白名单外键 → 硬失败
    if set(d) != POLL_NONTERMINAL_FIELDS:
        raise SnapshotContractViolation(...)          # 缺键 → 硬失败（对称强校验）
    for v in d.values():
        if isinstance(v, str) and _NONTERMINAL_ABS_PATH_RE.match(v):
            raise SnapshotContractViolation(...)      # 绝对路径泄露
    if len(json.dumps(dict(d), ensure_ascii=False).encode("utf-8")) > MAX_NONTERMINAL_SNAPSHOT_BYTES:
        raise SnapshotContractViolation(...)
```

复用既有 `SnapshotContractViolation(RuntimeError, AssertionError)` 双基类，保证 `python -O` 下仍能捕获。

### 4.4 `retry_after_seconds` 语义声明（不改值，只加文档）

值域仍钳制 `[2, 30]`。新增文档条款：**已完整消费 `wait_max_s` 的调用方应忽略 `retry_after_seconds` 并用自身节奏调度**。不修改值语义——避免破坏既有断言。

## 7. 关键红线与残余风险（诚实披露）

| # | 红线 / 残余风险 | 说明 |
|---|---|---|
| **R1** | **25s ↔ 30s 超时生死线** | 部分 Agent Host 有 30 s 工具调用超时。`wait_max_s=25` 仅余 5 s 余量（含网络/序列化）。**建议文档默认推荐 20 s**，25 s 保留为显式上限 |
| **R2** | **宿主串行化通知读取** | 若宿主在响应到达前不消费 `notifications/progress`，通知会在结尾批量到达——功能视觉上失效但**无害**。必须在 E4 走查中逐宿主确认（VS Code 通常实时消费；Theia 需实测） |
| **R3** | `progressToken` 复用 | MCP 规范要求每请求新 token。宿主复用会导致计数器回退，部分客户端可能丢弃通知。**服务端不可检测**，仅能文档约束 |

| **R6** | `reviewer_jobs.py` 与 `consultation.py` 的 `validate_job_id` 重复 | 非本次范围，但属客观 DRY 缺陷，建议后续单独立项（两处实现当前字节级一致，漂移风险潜伏） |

```python
async def watch(
    self,
    job_id: str,
    *,
    deadline_monotonic: float,
    min_interval_s: float = 0.05,
    max_interval_s: float = 1.0,
    liveness_probe_interval_s: float = 2.0,
) -> AsyncIterator[PollSnapshot]:
```

- `validate_job_id(job_id)` 前置（复用本模块既有实现）。
- 循环体：
  1. `snap = await anyio.to_thread.run_sync(self._read_snapshot_sync, jid)` —— **锁在此同步函数内获取并释放**。
  2. `yield snap`。
  3. `if snap.state in POLL_TERMINAL_STATES: return`。
  4. `if time.monotonic() >= deadline_monotonic: return`。
  5. `await anyio.sleep(min(interval, deadline - now))`；无状态变更时间隔翻倍封顶 `max_interval_s`；状态/phase 变更时重置为 `min_interval_s`。

- 代际自愈：读取到的 `JobRecord.generation` 若与上一轮不同，直接 yield 新快照并重置退避，**绝不抛异常**。
- 取消：不写任何 `except Exception`；`anyio` 取消异常自然向上传播。
- **零写盘铁律**：`watch()` 路径内禁止 `open(..., "w")`、禁 `enforce_unified_log_quota`、禁 `gc_by_filename_order`、禁状态迁移。
