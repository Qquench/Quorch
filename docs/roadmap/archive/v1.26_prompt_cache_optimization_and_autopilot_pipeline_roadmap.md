## 0. 背景、痛点与演进动因（Verdict & Motivation）

在 v1.25 交付双模编排拓扑与 Autopilot Harness 后，开发团队在实际高频推演与模型调用中观察到两个制约全自动开发体验的瓶颈：

1. **Prompt Cache 实际命中率未达预期（~53%）**：
   通过对 `.agents/logs/reviewer/cache_telemetry.jsonl` 中 228 条真实调用记录的分析，发现虽然 `audit` 模式缓存平均命中 6,700 tokens，但整体命中率仅为 53.7%，且流式调用记录全部显示为 0% 命中；经 Reviewer 架构推演诊断，其根因包含：
   - 流式 SSE 传输未下发/未提取 `include_usage`，造成遥测统计假盲区；
   - Windows 环境下代码切片注入包含 `\r\n`，文件轻微变更即导致前缀哈希全局失效；
   - 静态系统前缀未按 64-token Block 物理边界对齐，导致后序相同切片的 Token 序列偏移错位；
   - 多文件探查时的切片拼接顺序存在非确定性风险。
2. **Context Injector 遗留指令与 Autopilot 接力棒冲突导致的非预期刹车**：
   在 v1.25 中已实现 `harness_next_action` 全自动接力棒，但预调用 Hook（`context_injector.py`）仍保留了早期“发现待确认任务即命令模型停下并扔出架构交接卡”的硬编码引导语。这导致主模型在收到 Autopilot 连续接力动作（如 `PROPOSE`、`CONFIRM`）时，受到 Hook 提示词的相互撕扯，误以为必须停下回合等待人类介入，破坏了流水线的自动闭环体验。

## 1. 架构设计与技术方案（Technical Architecture）

### 1.1 Prompt Cache 梯度分层模型（Gradient Layering Model）

为了最大化利用现代大模型后端的 KV Cache 机制（如 DeepSeek 64-token Block Cache），Prompt 装配需遵循严格的自底向上不可变梯度层次：

```
+-------------------------------------------------------------------------+
| Layer 1: Static System Prefix                                           |
| (角色说明、原则纪律、输出契约)                                            |
| * 长度约束: 严格对齐至 64 的整数倍 token 边界 (例如通过 Whitespace /     |
|   固定注释填充对齐)，消除后续内容在 Block 边界上的漂移。                |
+-------------------------------------------------------------------------+
| Layer 2: Canonical Context Slices (AST 切片池)                         |
| (被审查目标文件、依赖声明、类型契约)                                      |
| * 确定性约束: 严格按 (rel_path, start_line, end_line) 稳定排序；         |
| * 编码约束: 严格 CRLF -> LF 规范化；                                    |
| * 跨轮次复用: 同一开发任务生命周期内，AST 上下文切片保持结构稳定。      |
+-------------------------------------------------------------------------+
| Layer 3: Dynamic Ephemeral Payload                                      |
| (当前具体审查指令、用户追问、临时会话标识)                               |
| * 位于序列最尾部，其动态变动绝不影响 Layer 1 和 Layer 2 的 Block 命中。   |
+-------------------------------------------------------------------------+
```

### 1.2 64-Token Block 对齐算法原理
设 Layer 1 的原始 token 长度为 $L_1$。
若 $L_1 \pmod{64} \neq 0$，则计算所需 padding 的 token 数量：
$$\Delta = (64 - (L_1 \pmod{64})) \pmod{64}$$
通过注入 $\Delta$ 长度的标准无语义空白或换行填充（若无法精确估计分词，则采用预计算的固定安全对齐模板），使得 Layer 2 的起始 Token 恰好落在第 $K \times 64$ 个 Token 的边界上，从而保证后续任意静态代码切片获得 100% 的 Block 级对齐复用。

### 1.3 Context Injector 协同契约与 Autopilot 接轨
`context_injector.py` 在向模型注入提示词前，必须探查当前有效编排模式与 `harness_next_action`：
- 若处于 Autopilot 连续推进态（`harness_next_action.action` 属于接力动作集合）：
  - 严禁下发“停下等待”、“输出交接卡”等刹车指令；
  - 注入高优先级接力引导：“当前处于 Autopilot 全自动流转状态，请直接遵照 harness_next_action.instruction 执行下一步，严禁中途停顿”。
- 仅当处于终态或断点停靠态（`PAUSE_FOR_ACCEPTANCE` / `BLOCKED` / `ROADMAP_DONE`）时，才允许下发停机与总结交付卡提示。
